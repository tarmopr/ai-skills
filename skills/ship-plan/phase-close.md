# Ship a plan: close phase

Sections 7 and 8 of [ship-plan](SKILL.md). Everything in SKILL.md applies here.

## 7. Close out

1. **Closing comment.**
   Four outcomes, one template each (templates-issue.md with an issue, templates-pr.md without):
   - **Done:** merged; the base branch green, or no CI (CI None, no base-branch run for the merge); and validation (section 6b) passed, apart from scenarios listed under **Not tested** and an `## After merge` failure this run's diff does not explain (reported). With an issue: "Issue comment: done", then the tracker's *Set status* to the done status, **only when `Done means:` is met** (with CI None, Done means is "merged"; scenarios under **Not tested** count only when `Done means:` names them). No issue: the host's *PR comment* with "PR comment: done".
     **Each `Tickets:` issue** gets the done status with the run issue, and only when all of these hold: the run issue got it; every plan task whose heading names its key is committed, none parked, skipped or left `[needs a decision]`; and the ledger's `Commits:` line counts at least one commit for it. Then "Issue comment: done (batch ticket)" and the tracker's *Set status* to the done status. Otherwise "Issue comment: not done (batch ticket)", naming what is missing; its status stays, and it goes in the batch. Under every other outcome, each `Tickets:` issue gets the run issue's comment for that outcome, and its status stays.
     Before writing the Done comment, read the `blockers.md` entries about what the base branch's CI (workflows or pipelines) does after a merge (for example a chart bump PR their bot opens and merges; they stay in `blockers.md` as symptom → fix, the `Fix:` naming the check), record `Used: ship-plan/blockers.md <heading>` for each, check each one, and report its real state in the comment.
   - **Base branch red:** merged, and the base branch still red, or a validation failure (section 6b) still unfixed. "Issue comment: base branch red" or "PR comment: base branch red"; the issue stays in the start status.
   - **Awaiting review:** the PR is open, green, and every comment so far is handled, but it waits on reviewers (section 4R, step 5). "Issue comment: awaiting review"; without an issue, the report only (the PR shows its own state). The issue stays in its status. The report says how to resume.
   - **Not merged:** the PR is still open for another reason (verify not clean, checks never registered, the base branch red before merge, a refused merge, a deploy `## Allowed` does not cover, 5 review rounds), or no PR exists. "Issue comment: not merged" or "PR comment: not merged"; with no PR and no issue, the report is the only record.
2. **When the ledger has a `Docs PR:` line and the code PR merged, read [docs-pr.md](docs-pr.md).**
3. **A next part:** when the outcome is Done and the plan names a next part (a later plan or issue), write a handoff for it as the ledger section says, but as `HANDOFF-next.md` when the `handoff` skill is unavailable, so it never overwrites the session-end `HANDOFF.md`. Its resume line is not the ledger section's: it starts that part: `/ship-plan <its plan path>`, or `/ship-issue <its key>` when it has no plan yet.
4. **Lessons** (section 8), except under "Awaiting review" and `Phase: 5 awaiting merge`: they wait for the run's final close-out.
5. **Report,** concise, in this order, once every background prerequisite still running is stopped (TaskStop):
   1. **Needs you:** the batch.
   2. Status: base branch green or red (or "no CI"), PR, merge SHA, the docs PR, the lessons PR (and why it stays open, if it does) or, under `## Logs` `Location: local`, the local store's path, the issue link if any, and the ledger's `Allowed:` lines (section 0, step 7).
   3. Gate and scenario tables (from `verify-and-fix`), the `Simplify:` line, every unknown config section, and every override line not applied.
   4. **Decisions made for you:** every `Ruling:`, each with what it costs if wrong.
   5. **Not tested:** what, and why.
   6. The lessons recorded, the ledger's `Removed:` lines with section 8's git-history line, and what section 8 proposes: each proposed shared-skill change, `## Allowed` line and loosening config line, with its exact text, and under `local` each tracked lesson with its target file.
6. **Mark the ledger** `Phase: done` when the outcome is Done, and if this run was started by `/loop`, end the report with "Done: stop the `/loop`." Every other outcome keeps the run open, so a later `/ship-plan` resumes it.
7. **First drop every question a standing answer settles:** grep the headings of `<logs>/ship-plan/interruptions.md` and `<logs>/ship-issue/interruptions.md` ([Reading the logs](SKILL.md#reading-the-logs)) for each question in the batch; a matching entry is applied, not asked, with a `Used:` line. Only what is left is asked.
   **Ask the batch once,** after the report, with `AskUserQuestion` when the answers are choices. When the user answers, carry on, even on a `Phase: done` ledger (section 0, step 2): run the pending scenarios once they have signed in, add a new tracker or PR comment, and record each answer in `interruptions.md` as section 8 says.
   **Before creating a follow-up issue,** whether this batch approved it or an earlier answer did (a `Ruling: user` line copied from `ship-issue`'s I3 batch), check that a reviewer has not filed it already. Read the PR's review bodies and comments (the host's *Fetch review items*), and search the tracker as the tracker's *Find an existing follow-up* says. When an issue already covers it, create nothing: name that issue in the Done comment's follow-ups, and record a `Ruling:` that quotes the line of it that covers the follow-up. Also grep `<logs>/ship-plan/*.md` and `<logs>/ship-issue/*.md` ([Reading the logs](SKILL.md#reading-the-logs)) for the follow-up's subject: a log entry can name the issue when a tracker text search misses it. Create each issue as the tracker's *Create an issue* says, and link it to the run issue as the tracker's *Link two issues* says. With `Tracker: none` there is no follow-up issue: it stays under Follow-ups.

## 8. Lessons

Last, after everything else: the merge, base-branch CI, validation (section
6b), the docs PR and the closing comment; then the report. On a branch from
`origin/<base>` (`docs/ship-plan-lessons-<yyyy-mm-dd>`), never on the feature branch.
Run `git fetch origin <base>` right before `git switch -c`. Then merge
the branch of every open lessons PR
(the host's *Find open PRs*, by search) that the lessons-PR guard (below)
allows into the new branch.
A guarded one is left out: its PR stays open, and the report names it as left
out, with the guard's reason. Each `Lesson:` line in the
ledger, `verify-and-fix`'s included (they name their target file), goes where
these rules say.

**Under `## Logs` `Location: local`** ([config-format.md](config-format.md#-logs)) this section makes no branch, commit or PR, so the branch steps above, the lessons-PR guard and the PR steps of both batch bullets are skipped. The logs are written by the same rules, in the local store, in place; with a batch, write its entries there as `Answer: pending` before you ask. Every other repo learning (an override file, a config row or line) is not written: the report proposes it with its exact text and target file, for the user to add in a normal PR (the feature-branch config exceptions still apply: `## Slack`, `Tracker:`, a drafted tracker section). A lessons PR opened before the switch to `local` is reported as needing a person to close or merge it. A refused write to the store is a `Lesson:` in the report, never retried another way.

- **Repo learnings are written, not proposed,** each in one home:
  - **A procedure, how-to, fact, failure path or step only this repo needs** goes into the matching override file, `.claude/ship-plan/<skill>/<file>.md`, created if missing, or a config row (`## Evidence`, `## UI testing` notes, a gate's `Notes`) under the narrowing rule below. An override may only add or make a rule stricter ([Repo override files](config-format.md#repo-override-files)).
  - **A tooling or environment problem that recurs** goes into `<logs>/ship-plan/blockers.md`: symptom → fix.
  - **A question that recurs** (pre-flight, mid-run, final) goes into `<logs>/ship-plan/interruptions.md` as a **standing answer**: the rule that lets the next run decide on its own. It never grants a permission: for a missing one it points to the proposed `## Allowed` line. A question asked for want of a permission recurs until that line exists, so it gets an entry even though a skill already says to ask it. A question the user answered "ask each time" gets no entry: the question batch handles it. **A ruling the user overturned** becomes a standing answer stating the corrected rule.
  - **A one-off,** or anything the config, an override file or a skill already settles, stays in the ledger and goes in no log.
  - **Under `ship-issue`** (the plan has a `From ship-issue` block): its `Asked:` lines (questions from phases I0–I6) go into `<logs>/ship-issue/interruptions.md` instead, by the same rules, created from [../ship-issue/log-formats.md](../ship-issue/log-formats.md) if missing.
  - **Calibration stays out of the logs:** for each question asked and each ruling overturned, write a `Lesson:` line in the ledger naming the part of the confidence test that failed (under `ship-issue`, also the I2 research step or `## Evidence` row that would have predicted it); the report lists it.
- **The logs,** on the lessons branch (under `local`, in the store), in their [log-formats.md](log-formats.md) format (create a missing log from it). Budgets: `blockers.md` 16 KB, each `interruptions.md` 8 KB. In this order:
  1. **Upkeep and compaction, before adding anything,** run in one `general-purpose` writer subagent at the `## Models` `Research` row; the session never reads a whole log itself. Its prompt names the lessons branch's checkout (under `local`, the store), the log paths, today's date, the ledger's `Used:` lines, the budgets and these rules. It edits the logs (and the override files or config rows a procedure moves to; under `local` it writes neither, and returns each move as a proposal with its exact text and target file) and returns nothing but the entries it removed, merged or moved, one line each with why. Record each as a ledger line `Removed: <log path> <heading> — <why>`. In each log, never deleting an entry the config or an override file names:
     - **Upkeep:** bump `Seen` once per run on every entry a `Used:` line names (`<n+1>×, last <today>`, however many lines name it); merge near-duplicates into one entry; delete an entry fixed at the root (the tool or gate no longer fails that way), promoted to the config, an override file or a skill, or unseen for 90 days. An entry with no `Seen:` line (old format) was last seen on its file's last git change (`git log -1 --format=%cs -- <log>`; under `local`, of its tracked copy, else today); rewrite it in the new format.
     - **Over budget:** compact the whole file once: rewrite each entry in the compact format, move procedures to their home (above; under `local`, propose the move and keep the entry, in the compact format, until a later run finds its home holds it, then remove it), merge, then delete the least recently seen until it is under budget, a procedure kept for moving last and never before its home holds it. The entries on what the base branch's CI does after a merge (section 7, step 1) stay in `blockers.md`, as symptom → fix.
  2. **The write gate:** list the headings ([Reading the logs](SKILL.md#reading-the-logs)). An entry that matches is updated (corrected, extended, or its `Seen` bumped), never added a second time. A new entry only for a problem or question that would likely happen again: a tool, gate, environment or decision future runs will meet.
  3. **The lessons PR body and the report** list the `Removed:` lines, so the user can veto, and say: "deleted entries can be restored from git history: `git log -p -- <log>`" (under `local`, the report alone, saying they cannot be restored). Upkeep and a compaction (a log over budget) merge like any lesson, in the same lessons PR.
- **Config lessons follow the narrowing rule** ([Loosening changes](config-format.md#loosening-changes)), in `.claude/ship-plan.md` on the same branch: one on its "may be written" list is written; a loosening change is proposed with its exact line, and written only when this run's batch approved it; a `## Allowed` line is never written. Exceptions, committed on the feature branch instead because the run needs them now: `## Slack` (section 0, step 6), `Tracker:` (section 0, step 5), and a drafted `## Jira`, `## Linear` or `## GitHub Issues`.
- **Generic learnings are proposed:** a lesson that would help every repo (a missing step, a wrong order, a rule that misfired) goes in the report as "proposed shared-skill change", with the exact text, written generically: no repo, team or org name, issue key, URL or repo command. Never edit the shared skill files.
- **Missing `## Allowed` permissions are proposed:** when the run was held up for want of an entry on the closed list (a refusal, a question the user had to answer to allow something, an action the user did by hand), the report proposes the exact `## Allowed` line and the reason, for the user to add ([`## Allowed`](config-format.md#-allowed)). A hold-up no entry fits is a proposed shared-skill change; a command the permission system refused gets its exact `allowed-tools` line proposed (settings never edited), and its `Lesson:` goes to `blockers.md` (symptom: the refusal; `Fix:` put that line in the batch at once).
- **A rule for the whole repo,** not for this loop: propose a change to the repo's agent instructions file (for example `CLAUDE.md`) in the report, with the exact text. Never edit it.
- **The lessons-PR guard:** before merging a lessons PR, or its branch into a new lessons branch, this run's or one an earlier session opened, `git fetch origin <lessons branch>`, then read its diff (`git diff origin/<base>...origin/<lessons branch>`). When it touches `## Allowed` or `## Logs`, or changes the config in a way not on the "may be written" list ([Loosening changes](config-format.md#loosening-changes)) that this run's batch did not approve, never merge it, even when it is green and mergeable, and leave its branch as it is: it stays open, without holding the run open, and the report links it as "lessons PR, left open: <line> — <why>" (`## Allowed` and `## Logs` are sections only a person edits; or the config change needs an approval in this run's batch).
- **Batch empty:** open a docs-only PR, record `Lessons PR: #<n>` in the ledger, and wait for its checks. A PR the guard stops is reported as the guard says. Otherwise, if the review rule (section 4R, step 1) needs no approval, merge it through sections 5–6; if it needs one, request the AI review (the host's *Request an AI review*), leave it open for review, and link it in the report as "lessons PR, needs approval"; it never holds the run open. Right before the report, read its review state again (the host's *Review state*). Approved, checks green and every review item answered: merge it through sections 5–6 instead of reporting it as needing approval.
- **Batch not empty:** commit and push the branch with those entries marked `Answer: pending` *before* you ask. When the answers come, fill them in (drop an entry answered "ask each time"), then open the PR and merge it the same way.

During the run, write lessons in the ledger as `Lesson:` lines, never in the
log files on the feature branch.
